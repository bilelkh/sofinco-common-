Comment fonctionnent RepresentativeExample, SimulatorCredit et SimulatorBlock côté CMS

Jahia 8.2 CND / JCR Mixin sofmix:simulatorCta Settings node central

🎯 Vue d'ensemble

Les 3 composants partagent une infrastructure commune reposant sur :

  • 1 settings node global sofnt:simulatorConfig (sous /sites/sofinco/contents/site-settings/simulator-config) — source unique pour les URLs cibles et les bornes amount
  • 1 mixin partagé sofmix:simulatorCta — fournit tous les champs CTA simulateur (label, project, sourceId, etc.)
  • 1 helper TS central lib/simulatorCta.ts — construit l'URL du simulateur Vue.js depuis les données mixin + settings

🧩 Mixin partagé sofmix:simulatorCta

Mutualise tous les champs nécessaires pour construire un CTA pointant vers le simulateur Vue.js Sofinco.

[sofmix:simulatorCta] mixin
 - ctaLabel          (string) i18n
 - product           (string, choicelist[resourceBundle]) < '','PB','CR','RAC','CR_S'
 - sourceId          (string)
 - simProject        (string, choicelist[resourceBundle]) < '','AUTO','FAMILY','WORKS','MISCELLANEOUS','RAC'
 - simSubProject     (string, choicelist[resourceBundle]) < ...
 - simLoa            (string, choicelist[resourceBundle]) < '','true','false'
 - simIdcatorigin    (string)
 - simHashFragment   (string)

🚀 Bénéfices de ce refactor (mixin sofmix:simulatorCta)

Avant ce refactor, chaque composant simulateur redéfinissait ses propres champs (project, subProject, creditType, sourceId…) avec des conventions divergentes. Voici ce qu'apporte la mutualisation.

🎯 Bénéfices côté architecture

DRY total

Les 8 champs CTA simulateur sont déclarés une seule fois dans le CND. Un nouveau composant simulateur n'a qu'à ajouter > sofmix:simulatorCta pour hériter de tout l'outillage.

Source de vérité unique

L'URL du simulateur est construite par une seule fonction : buildSimulatorCtaFromNode. Un bug ou une évolution = 1 endroit à patcher, propagation automatique aux 3 composants.

Cohérence garantie

Tous les CTAs simulateur produisent la même structure d'URL (mêmes clés params, même ordre, même contrat). Plus de divergence accidentelle entre composants.

🎨 Bénéfices côté éditeur Jahia

📝 UX uniforme

Quel que soit le composant (ProductHero, SimulatorCredit, SimulatorBlock…), l'éditeur voit les mêmes champs avec les mêmes labels FR. Pas de surprise au passage d'un composant à l'autre.

🌍 i18n centralisée

Les labels et descriptions sont définis une fois dans sofinco-template.properties sous le namespace sofmix_simulatorCta.*. Pas de duplication par composant.

📋 Choicelists partagées

Les valeurs (PB/CR/RAC, AUTO/FAMILY/WORKS…) et leurs libellés français sont mutualisés. Ajouter un nouveau produit/projet = 1 ligne CND + 1 ligne properties.

🛠️ Bénéfices côté développeur

⚡ Nouveau composant

Créer un nouveau composant simulateur (ex: SimulatorCardSlim) : 4 lignes de CND, le mapping appelle buildSimulatorCtaFromNode, et tu hérites de tout (URL, routing, tracking, fallbacks).

🧪 Tests centralisés

La logique URL est testée dans simulatorCta.test.ts (20+ fixtures table-driven). Les mappers composants n'ont qu'à mocker le helper — tests rapides et isolés.

🔒 Typage fort

Types SimulatorCtaProject, SimulatorCtaCreditType, SimulatorCtaInput exportés. Autocomplétion + erreurs compile-time si un mauvais code projet est passé.

🎁 Bénéfices indirects (effets de bord positifs)

Onboarding plus rapide

Un nouveau dev comprend une fois la sémantique simulateur (via le mixin) et l'applique partout. Pas N conventions à mémoriser.

Code review allégé

Quand un PR touche un composant simulateur, le reviewer sait que la logique URL vient du helper — pas besoin de revérifier les params à chaque fois.

Migration outillée

Les scripts Groovy (migrate-simulatorBlock-mixins.groovy) sont réutilisables comme template pour migrer d'autres composants futurs vers le mixin.
💡 Principe sous-jacent : Strangler Fig Pattern + Single Source of Truth. On a strangulé les implémentations divergentes V1 par un unique mixin V2, sans Big Bang ni rupture éditoriale.

⚙️ Settings node central — sofnt:simulatorConfig

Un seul node global qui centralise toute la config simulateur du site.

[sofnt:simulatorConfig] > jnt:content, sofmix:configs
 - simulatorBasePage     (weakreference, picker[type='page']) < jnt:page
 - simulatorRacBasePage  (weakreference, picker[type='page']) < jnt:page
 - amountMin             (long) = 150    autocreated < '[150,999999]'
 - amountMax             (long) = 999999 autocreated < '[150,999999]'
Path : /sites/sofinco/contents/site-settings/simulator-config
Initialisation : script Groovy init-simulator-settings.groovy à exécuter au déploiement.

simulatorBasePage

Page Jahia hébergeant le simulateur Vue.js standard (PB / CR / Auto / Travaux / Famille).

simulatorRacBasePage

Page Jahia hébergeant le simulateur Vue.js en mode Rachat de Crédit.

amountMin / amountMax

Bornes globales pour les inputs montant — modifier ici impacte SimulatorCredit ET SimulatorBlock simultanément.

🔄 Flow JCR → React props

Quand une page contenant un de ces composants est rendue :

1
Jahia instancie le composant via default.server.tsx avec currentNode et renderContext
2
Le mapper.ts est appelé : il lit les props du node JCR + du mixin sofmix:simulatorCta
3
Le mapper appelle buildSimulatorCtaFromNode qui : (a) résout le basePath depuis le settings node, (b) calcule le hash route Vue.js, (c) sérialise les params URL
4
Le mapper appelle resolveAmountBounds qui lit amountMin/amountMax depuis le settings node
5
Les props finales sont passées au composant React DS (HeroSimulator, SimulatorBlock, etc.)

🎨 UI éditeur — JSON form overrides

Chaque composant a un fichier settings/content-editor-forms/forms/sofnt_xxx.json qui :

  • Ordonne les champs (rank) : jcr:title → amountPlaceholder → mixin CTA
  • Cache les champs mixin pas pertinents (ex: simHashFragment avancé)
  • Cache les fieldsets legacy (sofmix:cta + sofmix:ctaInternal/External sur SimulatorCredit)
  • Cache les bornes locales amountMin/amountMax sur SimulatorCredit pour forcer la lecture du settings global

  "nodeType": "sofnt:simulatorCredit",

📖 Cheat sheet — Détail de chaque champ du mixin sofmix:simulatorCta

Pour chaque champ : à quoi il sert, valeurs possibles, exemple concret d'URL générée.

ctaLabel string · i18n
Texte affiché sur le bouton submit du form simulateur.
Exemple : "Je simule mon prêt auto"
→ Bouton rendu : <button>Je simule mon prêt auto</button>
Si vide → fallback sur la translation simulatorCta.defaultLabel = "Je simule".
product choicelist · '','PB','CR','RAC','CR_S'
Type de crédit pré-rempli dans le simulateur Vue.js (saute l'étape « choix du produit »).
Valeur CNDSens métier
PBPrêt Personnel
CRCrédit Renouvelable
RACRachat de Crédit
CR_SCrédit Renouvelable spécifique
Exemple product=PB :
/parcours-simulateur?predefinedCreditType=PB#/
Côté URL la clé devient predefinedCreditType (contrat simulateur Vue.js).
sourceId string (libre)
Identifiant de source utilisé pour le tracking et l'attribution commerciale. Conventionnellement préfixé par NEOURL.
Exemple : sourceId="NEOURL14"
/parcours-simulateur?sourceId=NEOURL14#/
Différent par campagne marketing. Demande à l'équipe digital marketing le bon NEOURL.
simProject choicelist · '','AUTO','FAMILY','WORKS','MISCELLANEOUS','RAC'
Catégorie de projet du simulateur. Détermine la route hash Vue.js d'arrivée.
ValeurRoute Vue.jsPage simulateur
AUTO#/autoAuto / véhicule
FAMILY#/famille-loisirsFamille & loisirs
WORKS#/travauxTravaux
MISCELLANEOUS#/autreAutres projets
RAC#/rachat/nombre-creditsRachat de crédit
(vide)#/Home simulateur (choix manuel)
Exemple simProject=AUTO :
/parcours-simulateur?project=AUTO#/auto
simProject=RAC → bascule automatique vers simulatorRacBasePage au lieu de simulatorBasePage.
simSubProject choicelist (15 valeurs)
Sous-catégorie de projet — précise l'usage exact. Cohérence requise avec simProject.
simProjectsimSubProject autorisés
AUTOAUTO_COMBUSTION, AUTO_ELECTRIC_HYBRID
FAMILYFAMILY_MOVING, FAMILY_WEDDING, FAMILY_HEALTH, FAMILY_RECREATION, FAMILY_TRAVEL, FAMILY_OTHER
WORKSWORK_ENERGY_RENOVATION, WORK_DECORATION
MISCELLANEOUSMISC_FURNITURE, MISC_MOTORCYCLE, MISC_UNEXPECTED, MISC_ELECTRONIC_DEVICE, MISC_OTHER
RACRAC_RAC (hardcodé)
Exemple simProject=FAMILY + simSubProject=FAMILY_WEDDING :
/parcours-simulateur?project=FAMILY&subProject=FAMILY_WEDDING#/montant-financement
Avec project + subProject définis, le hash devient #/montant-financement (saute l'étape sélection projet → directement à la saisie du montant).
simLoa choicelist · '','true','false'
Mode LOA (Location avec Option d'Achat) — applicable principalement aux simulateurs auto.
Exemple simProject=AUTO + simLoa=true :
/parcours-simulateur?project=AUTO&loa=true#/auto
Laisser vide pour utiliser le comportement par défaut du simulateur.
simIdcatorigin string
Catégorie d'origine pour le tracking Eulerian. Si laissé vide, hérite automatiquement de l'idcat de la page Jahia courante (via mixin spmix:eaPageOptions).
Exemple simIdcatorigin="home_page" :
/parcours-simulateur?idcatorigin=home_page&project=AUTO#/auto
Ne le remplir QUE si tu veux un override spécifique pour ce CTA. Sinon laisse vide pour hériter de la page (DRY).
simHashFragment string (avancé)
Override de la route d'arrivée dans le simulateur. Court-circuite le calcul automatique basé sur project/subProject.
Exemple simHashFragment="/resultats" :
/parcours-simulateur?project=AUTO#/resultats
Réservé aux cas avancés où l'on veut atterrir sur une étape précise (ex: page résultats pour démo). À éviter en usage normal.

🛡️ Sécurité & fallbacks

Settings absent

Le helper retombe sur /parcours-simulateur(-rac) hardcodés — zéro panne site-wide

JS désactivé

Form GET natif fonctionne — perte du hash mais le simulateur Vue.js route via query params (resumeSimulator())

Mixin pas configuré

L'URL fallback est la home simulateur — l'utilisateur sélectionne manuellement son projet
